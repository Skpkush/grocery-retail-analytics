# Copilot safety

_Generated by `python -m retail.docs_gen`: every row below is the copilot's real response, in offline (deterministic) mode._

The copilot is a differentiator, not the centre of the project. It may only:

- run **one read-only SELECT** on warehouse tables, through `src/retail/sql_guard.py`;
- answer from the **approved SQL library**, metric-layer templates or the project documentation;
- **refuse** questions the data cannot answer, rather than return a plausible-looking table;
- **attach the caveat** to answers about associations and proxies, so they are never stated as proven effects;
- **cite its sources** and write every question to an audit log (`data/audit_log.jsonl`).

## Defence in depth

1. **Routing:** write requests, prompt injection and unsupported topics are refused before any SQL is planned.
2. **Validation:** a single SELECT/WITH only. DDL, DML, settings, extensions and file functions are rejected after comments and string literals are masked.
3. **Connection:** DuckDB opens with `read_only=True` and `enable_external_access=false`, so even SQL that passed validation cannot write, read local files or load extensions. A test (`tests/test_sql_guard.py`) runs writes and file reads directly on this connection and expects them to fail.
4. **Row cap:** results are wrapped in an outer `LIMIT`.
5. **Evaluation:** `evals/golden_questions.json` includes refusal and caveat cases, and CI fails below a 90% pass rate.
